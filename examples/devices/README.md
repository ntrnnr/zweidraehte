# `zweidraehte-devices` — device definitions

Transport-agnostic KNX device **definitions** (parameters, communication
objects, and — for the host-side demos — ETS page layouts). No binaries: the
firmware targets in `firmware/` bind these to a concrete transport/platform,
and the generators in `examples/generators/` render their MTXML / `.knxprod`.
The library is named `devices`, so consumers write `use devices::…`.

Two tiers of definition:

- **`no_std` firmware definitions** (`light_switch`, `ip_interface`) — consumed
  by the embedded and Linux host firmware targets. Always compiled.
- **Host-side demo/replication definitions** (`system_b_demo`,
  `mdt_push_button_lite`, `module_test_device`) — gated behind the **`demos`**
  feature (a *default* feature, so `cargo test -p zweidraehte-devices` covers
  them). They pull in `zweidraehte-knxprod` for the page layout; firmware
  consumers take `default-features = false` and never see them.

`light_switch` is deliberately split so both device stacks share one product:
`params.rs`, `comm_objs.rs`, `layout.rs`, `translations.rs` and `behavior.rs`
are stack-neutral (one `#[ets_com_objects]` declaration, one normalized
button/application reducer), while `full/` binds them to `zweidraehte-device`
and `micro/` to `zweidraehte-microdevice`. The two halves are behind the
**`full`** and **`micro`** features, so a firmware target compiles only the
stack it uses; the `micro` path never pulls in embassy. That split is what
makes the full-vs-micro comparison on identical hardware meaningful — the
behaviour and the ETS metadata are literally the same code.

## Device identity reference

All IDs are hex. **Manufacturer 00FA** is our own test manufacturer; **0083**
is MDT (used only by the replicated MDT device). "App ID" is the ETS
`ApplicationNumber`; the same physical device may expose several app IDs so
distinct medium/secure variants coexist in one catalogue.

### `light_switch` — 2-button light switch (`no_std`, always built)

One application logic, one parameter/CO set, one page layout — replicated
across every medium and secure/insecure combination. Manufacturer `00FA`,
app version `02`, tables ADT 10 / AST 12 / CO 6.

| Variant | Mask | App ID | HW type | HW serial | Firmware target |
|---|---|---|---|---|---|
| KNX/IP | SystemBKnxIp `57B0` | `0300` | `…00 03` | `00FA 0000 0003` | `firmware/linux/eth_light_switch`, `firmware/rp2040/eth_light_switch` |
| KNX/IP Secure (IP-Secure + Data-Secure) | SystemBKnxIp `57B0` | `0305` | `…00 03` | `00FA 0000 0009` | `firmware/linux/eth_secure_light_switch`, `firmware/rp2040/eth_secure_light_switch` |
| TP1 | SystemBTp1 `07B0` | `0301` | `…00 03` | `00FA 0000 0004` | `firmware/stm32/g0_tp1_light_switch`, `firmware/rp2040/tp1_light_switch` |
| TP1 Data Secure | SystemBTp1 `07B0` | `0302` | `…00 03` | `00FA 0000 0005` | `firmware/stm32/g0_tp1_secure_light_switch` |
| KNX-RF | SystemBRf `27B0` | `0303` | `…00 03` | `00FA 0000 0006` | `firmware/stm32/g0_knxrf_device` |
| KNX-RF Data Secure | SystemBRf `27B0` | `0304` | `…00 03` | `00FA 0000 0007` | `firmware/stm32/g0_knxrf_secure_light_switch` |
| KNX-RF Data Secure (retransmitter) | SystemBRf `27B0` | `0304` | `…00 03` | `00FA 0000 0008` | `firmware/stm32/g0_knxrf_secure_retransmitter` |
| System 7 TP1 | System7Tp1 `0705` | `0306` | `…00 0A` | `00FA 0000 000A` | `firmware/stm32/g0_tp1_system7_light_switch`, `firmware/stm32/g0_tp1_micro_system7_light_switch` |
| System 7 TP1 Data Secure | System7Tp1 `0705` | `0307` | `…00 0B` | `00FA 0000 000B` | `firmware/stm32/g0_tp1_system7_secure_light_switch` |
| BCU2 TP1 | BCU2 `0020` | `0308` | `…00 0C` | `00FA 0000 000C` | `firmware/stm32/g0_tp1_bcu2_light_switch` |
| BCU2 TP1 Data Secure | BCU2 `0021` | `0309` | `…00 0D` | `00FA 0000 000D` | `firmware/stm32/g0_tp1_bcu2_secure_light_switch` |

System B and System 7 do **not** use a different mask for Data Secure; their
secure variants get a separate app ID so both coexist in one `.knxprod`.
BCU2 is the exception backed by the target device: plain is 0020h and Data
Secure is its 0021h sibling. Generated by
`examples/generators/src/bin/gen_light_switch_mtxml.rs` (`gen_light_switch_mtxml`).
The full and micro System 7 firmware use the same product entry and EEPROM
layout; both BCU2 entries use the generator's first-class absolute-segment
layout and boot-image prefixes produced from the same communication-object
metadata. The micro-stack rows (both BCU2 variants, and the micro half of the
System 7 row) are experimental targets on `zweidraehte-microdevice` —
they exist to compare the two stacks on identical hardware, not as
finished products.

## Regenerating

```bash
cargo run --bin gen_light_switch_mtxml            # light switch, all variants (IP … RF-secure)
cargo run --bin gen_light_switch_mtxml -- --knxprod  # signed .knxprod (needs converter_key.xml)
cargo run --bin gen_ip_interface_mtxml            # IP interface
cargo run --bin gen_mtxml                         # system_b_demo
cargo run --bin gen_module_mtxml                  # module test device
cargo run --bin gen_mdt_mtxml                     # MDT replication
```
